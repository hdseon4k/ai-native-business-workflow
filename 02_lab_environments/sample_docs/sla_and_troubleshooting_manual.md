## 1. 사내 서비스 수준 계약(SLA) 정책 및 고객사 계약 등급별 보장 규정

본 규정은 당사의 클라우드 플랫폼 및 엔터프라이즈 B2B 서비스를 이용하는 모든 고객사의 장애 발생 시 대응 기준, 서비스 가용성 보장 수준, 그리고 목표 복구 시간을 규정합니다.

### 1.1 고객사 계약 등급(Tier) 분류 체계
당사의 고객사는 서비스 계약 규모, 월간 거래액(GMV), 그리고 비즈니스 중요도에 따라 3개 등급으로 분류됩니다.

1. **VIP 등급**:
   - 대상: 핵심 전략 파트너사, 월 매출 10억 원 이상 고객사, 실시간 금융/결제/대규모 이커머스 기업.
   - 보장 가용성: **99.99%** (월간 허용 다운타임 4.38분 이내).
   - 배정 인력: 24/7 전담 SRE 온콜 엔지니어 및 전담 Account Manager(AM) 핫라인 배정.
2. **Enterprise 등급**:
   - 대상: 일반 기업형 연간 구독 고객사, 물류/제조/바이오 중견 엔터프라이즈.
   - 보장 가용성: **99.9%** (월간 허용 다운타임 43.8분 이내).
   - 배정 인력: 24/7 엔지니어링 온콜 풀 지원.
3. **Standard 등급**:
   - 대상: 기본 라이선스 플랜 이용 고객사, 스타트업 및 소규모 개발팀.
   - 보장 가용성: **99.5%** (월간 허용 다운타임 3.65시간 이내).
   - 배정 인력: 주간(09:00~18:00) 티켓 접수 및 순차 지원.

### 1.2 계약 등급별 SLA 대응 및 복구 목표 시간 매트릭스

장애 인시던트 인입 시점부터 최초 전문 엔지니어의 공식 응답(First Response) 및 목표 복구 시간(MTTR)은 다음 표의 기준을 엄격히 준수해야 합니다.

| 계약 등급 (Tier) | 목표 최초 응답 시간 (SLA Response) | 목표 복구 시간 (MTTR - Critical) | 장애 상황 브리핑 주기 | 전담 AM 통보 기한 |
| :--- | :--- | :--- | :--- | :--- |
| **VIP** | **15분 이내** (최우선 긴급 배정) | **60분 이내** | 매 15분 단위 현황 공유 | 접수 즉시 (5분 이내) |
| **Enterprise** | **60분 이내** | **180분 이내** | 매 60분 단위 현황 공유 | 30분 이내 |
| **Standard** | **240분 이내** (4시간 이내) | **480분 이내** (영업일 기준) | 상태 변경 시 웹 대시보드 공지 | 해당 없음 |

### 1.3 SLA 위반 시 보상 크레딧(Service Credit) 산정 및 지급 규정

당사의 귀책사유로 인해 명시된 SLA 응답 시간 또는 복구 목표 시간을 초과하여 서비스 장애가 지속된 경우, 고객사는 아래의 공식 산정 기준에 따라 익월 청구 금액에서 공제되는 서비스 크레딧을 청구할 수 있습니다.

- **보상 크레딧 산정 공식**:
  $$\text{Service Credit (KRW)} = \text{월 청구 기본 이용료} \times \text{지급률(\%)}$$
- **지급률(%) 산정 기준표**:
  - **VIP 고객사**:
    - 최초 응답 시간(15분) 초과: 당월 청구액의 **10%** 보상
    - 누적 다운타임 60분 초과 ~ 120분 이하: 당월 청구액의 **25%** 보상
    - 누적 다운타임 120분 초과: 당월 청구액의 **50%** 전액 환급 및 위약금 면제 협의
  - **Enterprise 고객사**:
    - 최초 응답 시간(60분) 초과: 당월 청구액의 **5%** 보상
    - 누적 다운타임 180분 초과: 당월 청구액의 **15%** 보상
  - **Standard 고객사**:
    - 누적 다운타임 480분 초과 시 당월 청구액의 **5%** 크레딧 적립
- **고위험 보상 조치 통제 (Human-in-the-Loop 필수)**:
  - AI 에이전트는 보상 크레딧 지급 권고안을 작성할 수 있으나, **100만 원 이상의 크레딧 발행 또는 VIP 고객사 대상 보상 지급 조치는 반드시 영업총괄이사(AM Lead)와 재무팀의 사전 승인(HITL)을 획득**한 후 집행되어야 합니다.

## 2. 장애 심각도(Severity) 판정 기준 및 비상 에스컬레이션 매트릭스

장애 인시던트 접수 시 시스템 모니터링 메트릭 및 고객 신고 내용을 바탕으로 다음의 4단계 심각도 등급으로 자동 분류됩니다.

### 2.1 심각도 등급 정의
1. **Critical (P1 - 긴급 치명 장애)**:
   - 전사 메인 결제 시스템 다운, 데이터베이스 커넥션 완전 고갈로 인한 주문 불가, 또는 통합 인증 서버 마비로 전체 사용자의 로그인이 차단된 상태.
   - VIP 고객사의 핵심 트래픽 경로가 100% 두절된 경우.
2. **High (P2 - 주요 기능 장애)**:
   - 시스템의 핵심 기능은 동작하나, 특정 주요 모듈(배송 추적, 정산 배치, 알림 발송 등)이 다운되어 처리량이 50% 이상 급감한 상태.
   - WAS 컨테이너의 메모리 누수로 인해 재기동 직전인 상태.
3. **Medium (P3 - 부분 기능 저하)**:
   - 우회 수단(Workaround)이 존재하며, 일부 비핵심 기능의 레이턴시 증가 또는 대량 데이터 파일 전송 속도 저하.
4. **Low (P4 - 단순 문의 및 경미한 결함)**:
   - 서비스 운영에 직접적 영향이 없는 UI 렌더링 오차, 정적 문서 오탈자, 단순 설정 안내 요청.

## 3. 장애 유형별 표준 복구 절차서 (Standard Runbooks / SOP)

### 3.1 [Runbook-01] RDBMS 데이터베이스 커넥션 풀(Connection Pool) 고갈 장애

#### 3.1.1 장애 징후 및 임계치
- **이상 징후**: 모니터링 시스템에서 `db-primary-01` 서버의 `db_connection_pool_usage.pool_usage_pct` 값이 **90.0% 이상**으로 지속되며, 클라이언트 대기 큐(`waiting_clients`)가 20개 이상 발생.
- **영향도**: 신규 트랜잭션 획득 실패로 인한 HTTP 500 에러 및 타임아웃 연쇄 폭증.

#### 3.1.2 표준 대응 단계 (Step-by-Step)
1. **1단계: 상태 및 메트릭 교차 검증**:
   - 모니터링 API(`GET /api/v1/metrics/db-primary-01`)를 호출하여 현재 활성 커넥션(`active_connections`), 최대 커넥션(`max_connections`), 풀 점유율을 확인합니다.
2. **2단계: 위험도 평가 및 승인 게이트웨이(HITL) 가동**:
   - DB 커넥션 풀 초기화(`reset-db-pool`)는 기존의 유휴/비정상 세션을 강제 종료하는 파괴적 조치이므로 **고위험(High Risk)** 액션으로 간주됩니다.
   - 해당 장애 티켓의 고객사가 **VIP 또는 Enterprise** 등급인 경우, **절대로 AI 에이전트가 단독으로 풀을 초기화할 수 없으며**, 반드시 당직 온콜 리드(Lead SRE)에게 승인 웹훅 알림을 전송해야 합니다.
3. **3단계: 조치 API 실행 (`reset-db-pool`)**:
   - 승인자가 결재를 완료하면 n8n 또는 자동화 시스템은 사내 모사 API 서버로 다음 규격의 조치 요청을 전송합니다:
     - **Endpoint**: `POST /api/v1/actions/reset-db-pool`
     - **Payload**:
       ```json
       {
         "server_id": "db-primary-01",
         "reason": "TKT-2026-001 인시던트에 따른 VIP 고객 결제 지연 해소를 위한 커넥션 강제 회수",
         "authorized_by": "lead_sre_kim@enterprise.internal",
         "ticket_id": "TKT-2026-001"
       }
       ```
4. **4단계: 정상화 확인 및 감사 로그 기록**:
   - 조치 실행 후 반환된 `transaction_id`를 확인하고, 1분 후 `GET /api/v1/metrics/db-primary-01`을 재호출하여 `pool_usage_pct`가 20% 이하의 `healthy` 상태로 복구되었는지 검증합니다.
   - `audit_logs` 테이블에 승인자, 트랜잭션 ID, 복구 메트릭 결과를 영구 기록합니다.

### 3.2 [Runbook-02] 애플리케이션 WAS 메모리 누수(OOM / Heap Exhaustion) 대응

#### 3.2.1 장애 징후 및 임계치
- **이상 징후**: `app-was-01` 등 애플리케이션 파드의 JVM 힙 메모리 사용률이 **90% 이상**에 도달하고, Full GC 실행 주기가 5초 미만으로 단축되며 CPU 사용률이 스파이크를 일으킴.

#### 3.2.2 표준 대응 단계 (Step-by-Step)
1. **1단계: 힙 덤프(Heap Dump) 자동 백업**:
   - 인스턴스 종료 전 사후 원인 분석을 위해 프로파일러 덤프 스크립트를 백그라운드로 실행합니다.
2. **2단계: 트래픽 드레인 및 무중단 롤링 재기동 (Low Risk)**:
   - 해당 서비스는 다중화(K8s Replica 4대 이상)되어 있으므로, 단일 WAS 노드의 롤링 재기동은 서비스 중단을 유발하지 않는 **저위험(Low Risk)** 액션입니다.
   - AI 에이전트는 별도의 사람 승인 대기 없이 즉시 대상 파드의 트래픽을 차단(Cordon)하고 순차 재기동 명령을 수행할 수 있습니다.
3. **3단계: 정상 복구 모니터링**:
   - 컨테이너 헬스체크 프로브(`/healthz`)가 정상 200 OK를 반환하는지 3회 연속 확인 후 인그레스 트래픽을 재개합니다.

### 3.3 [Runbook-03] 통합 사내 SSO 및 OAuth2 인증 게이트웨이 타임아웃 대응

#### 3.3.1 장애 징후 및 임계치
- **이상 징후**: `auth-api-01` 서버의 HTTP 504 Gateway Timeout 발생 비율이 5%를 초과하며, 사용자 로그인 인증 지연시간이 3,000ms를 초과.

#### 3.3.2 표준 대응 단계 (Step-by-Step)
1. **1단계: 세션 캐시(Redis Cluster) 연결 상태 점검**:
   - 인증 토큰 만료 처리 데몬의 락(Lock) 경합 여부를 확인합니다.
2. **2단계: 서킷 브레이커(Circuit Breaker) 수동 트립**:
   - 백엔드 LDAP/AD 서버 부하 경감을 위해 비필수 부가 인증(2FA 간편인증 일부)을 임시 폴백 모드로 격리합니다.
3. **3단계: 긴급 에스컬레이션**:
   - 인증 장애는 즉시 P1(Critical)으로 승격되므로 보안팀 및 계정운영팀 온콜 채널에 5분 이내 자동 브리핑을 게시합니다.

## 4. 보안 거버넌스 및 감사 추적(Audit Trail) 불변성 원칙

1. **무단 단독 실행 금지 (Zero-Trust Principle)**:
   - 운영 서버의 상태를 변경하거나 데이터를 수정·삭제하는 모든 액션은 반드시 고유한 실행 권한 토큰을 지녀야 합니다.
2. **감사 로그(Audit Trail) 필수 기록 항목**:
   - AI 워크플로우에 의해 호출되는 모든 외부 API 및 DB 트랜잭션은 `audit_logs` 테이블에 아래 항목을 반드시 JSON 형태로 남겨야 합니다:
     - `workflow_name`: 실행된 n8n 워크플로우 명칭
     - `action_type`: 실행된 액션 종류 (예: `RESET_DB_POOL`, `ISSUE_CREDIT`, `ESCALATE_TICKET`)
     - `actor`: 요청 주체 (예: `n8n_agent_w4`, `lead_sre_kim`)
     - `payload_json`: 조치 당시의 메트릭 스냅샷, 승인 토큰, 실행 결과 반환값
     - `executed_at`: UTC 기준 실행 타임스탬프
